# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` – `start` build (L35) | `punch_in` is a naive UTC datetime but the code replaces `hour/minute` on it as though it were IST, making shift_start an incorrect UTC instant. On an IST host the difference is 5h30m, so grace periods and late counts are entirely wrong. | Any test comparing `late_minutes` against a known value – e.g. punch-in 09:40:01 IST would appear as 0 min late because the helper compares UTC 09:40 against UTC 09:30. | Convert `punch_in` to IST first, then build shift_start on the attendance IST date; compare both in UTC. |
| 2 | `compute_late_minutes` – condition (L37) | `minutes > 10` uses the correct strict inequality, but only for positive offsets. Negative values (punch before shift_start) would give `minutes < 0`, which is not `> 10`, so the function returns 0 – that part is fine. However the whole function is broken due to defect 1 making the value meaningless. | Same as defect 1. | Fixed via defect 1 fix; condition `> 10` kept (correct per R2). |
| 3 | `compute_work_hours` – rounding (L41) | `round(..., 2)` uses Python's banker's rounding (round-half-to-even), not half-up as required by R4. `round(2.5) == 2` in Python. | Work duration landing exactly on a .005-hour boundary: e.g. 9000 s = 2.500 h → Python returns 2.5 (coincidentally OK); 16200 s = 4.500 h → Python may round to 4.5 (OK) or 4.4 depending on float precision. A test suite with exact boundary values will catch mismatches. | Replaced with `decimal.Decimal.quantize(ROUND_HALF_UP)`. |
| 4 | `compute_overtime` – timezone mismatch (L46) | `end` is built as a tz-aware `IST` datetime, but `punch_out` is a naive UTC datetime. Subtracting them raises `TypeError: can't subtract offset-naive and offset-aware datetimes` at runtime. | Any call to punch-out → 500 crash. | Pass punch_out and shift_end in consistent naive UTC; build the shift_end datetime in IST and convert to UTC before subtracting. |
| 5 | `compute_overtime` – missing 30-minute threshold (L47) | Returns `max(0, ot_minutes)` without checking `>= 30`, so 1–29 min of overtime are incorrectly reported. R3 says overtime is counted only when `>= 30`. | Employee punches out 25 min after shift_end → `overtime_minutes = 25` (should be 0). | Added `return ot_min if ot_min >= 30 else 0`. |
| 6 | `compute_overtime` – overnight shift wrong date (L46) | For overnight shifts (`shift_end <= shift_start`), shift_end falls on the *next* calendar day. The starter code uses `date_str` (the shift-start day) to build the shift_end datetime, so overtime is computed relative to 06:00 on the wrong day — punch_out on the second day appears negative. | Employee EMP0005 (22:00–06:00), punch_out 06:40 next day → computed overtime is negative, clamped to 0, not 40 min. | Detect overnight flag; if overnight, add 1 day to the base date before setting `hour/minute`. |
| 7 | `/health` – no MongoDB ping (L73–74) | Always returns `{"status": "ok"}` regardless of MongoDB connectivity. The spec requires 503 when MongoDB is unreachable. | Start app with wrong `MONGO_URI` or stop MongoDB → `/health` still returns 200; the grader's readiness poll cannot detect a down database. | Wrapped in `db.command("ping")` / `except` → 503. |
| 8 | `POST /employees` – check-then-insert race (L79–80) | `find_one` then `insert_one` is not atomic. Two concurrent requests with the same `emp_code` both pass the `find_one` check, both call `insert_one`, and both succeed → 2 documents, neither gets 409. | Send two simultaneous POST requests with the same `emp_code`. | Created a unique index on `employees.emp_code`; wrapped `insert_one` in `try/except DuplicateKeyError → 409`. |
| 9 | `POST /employees` – naive local datetime (L82) | `datetime.now()` returns the local timezone's time without tzinfo. On a UTC+05:30 host `created_at` is stored 5.5 h ahead of UTC. Returned in the response as a Python `datetime` object, which FastAPI serialises as an ISO string, not as epoch ms. | Response body has `"created_at": "2026-07-06T09:28:00"` instead of an integer; on non-IST hosts the stored value is wrong. | Used `datetime.utcnow()` (naive UTC, consistent with PyMongo default); serialize to epoch ms before returning. |
| 10 | `POST /employees` – response exposes `_id` / wrong `created_at` type (L84–85) | `doc.pop("_id", None)` is correct but `doc["created_at"]` is still a `datetime` object. FastAPI returns a string, not an integer, violating the `EpochMillis` schema. | Response validation or grader schema check catches `created_at` as a string. | Added `_ser_employee()` helper that converts `created_at` to epoch ms. |
| 11 | `POST /employees` – no input validation (L53–60) | `EmployeeIn` model has no patterns or constraints; invalid `emp_code`, `email`, `shift_start`/`shift_end` are accepted silently. No check that `shift_start != shift_end`. | POST `{"emp_code": "BADCODE", "email": "notanemail", ...}` → 201. | Added `pattern=` constraints on `emp_code`, `email`, `shift_start`, `shift_end`; added `@model_validator` for `shift_start != shift_end`. |
| 12 | `GET /employees` – wrong pagination offset (L93) | `skip = page * page_size` — for page 1 this skips `page_size` rows (the first page), returning page 2's data. Correct formula is `(page - 1) * page_size`. | `GET /employees?page=1` returns items that should be on page 2; page 1 is unreachable. | Changed to `skip = (page - 1) * page_size`. |
| 13 | `GET /employees` – total ignores filter (L94) | `count_documents({})` counts all employees regardless of the `department` filter, so `total` is always the full headcount. Violates R10 ("total always reflects the applied filters"). | `GET /employees?department=Sales` → total is 6 instead of 2. | Changed to `count_documents(q)` where `q` contains the filter. |
| 14 | `GET /employees` – not sorted (L95) | No `.sort()` call; documents are returned in insertion order, not `emp_code` ascending. | Listing order is non-deterministic / insertion-order. | Added `.sort("emp_code", ASCENDING)`. |
| 15 | `GET /employees` – `created_at` not serialised (L95) | `find()` returns raw documents; `created_at` is a `datetime` object, serialised by FastAPI as an ISO string. | Response schema mismatch (integer expected, string returned). | Applied `_ser_employee()` to each item. |
| 16 | `POST /attendance/punch-in` – no 404 guard (L101) | If `db.employees.find_one(...)` returns `None`, the code proceeds and crashes on `emp["shift_start"]` with a `KeyError` → 500. | Punch-in for an unknown `emp_code` → 500 instead of 404. | Added `if not emp: raise HTTPException(404, ...)`. |
| 17 | `POST /attendance/punch-in` – naive UTC not IST for date (L102–103) | `datetime.fromtimestamp(ms/1000)` (without tz) creates a local-time datetime. `ts.date()` then returns the local date, not the IST date. Off by 1 day for punch-ins between 18:30–23:59 IST on non-IST hosts. | Employee on IST punches in at 23:00 IST; host is UTC → `ts.date()` gives UTC date (the day before). | Used `ms_to_dt()` (naive UTC) then `_attendance_date()` to derive IST date per R1, including overnight shift logic. |
| 18 | `POST /attendance/punch-in` – R1 second truncation missing (L102) | `datetime.fromtimestamp(ms/1000)` preserves sub-second fractions if the division is not integer. Should floor to whole seconds before any calculation (R1). | Punch-in at epoch ms whose `ms % 1000 != 0` stores a sub-second datetime; late_minutes off by <1 min in edge cases. | `ms_to_dt` uses `ms // 1000` (integer division) to truncate. |
| 19 | `POST /attendance/punch-in` – check-then-insert race (L104–105) | Same pattern as defect 8: `find_one` + `insert_one` is not atomic for duplicate-date detection. | Two simultaneous punch-ins for the same (emp_code, date) both succeed. | Created unique compound index on `(emp_code, date)`; wrapped insert in `try/except DuplicateKeyError → 409`. |
| 20 | `POST /attendance/punch-in` – status not validated (L109) | `status` field on `PunchInIn` is a plain `str` with default `"PRESENT"`; any string is accepted. ABSENT or LEAVE would be stored via punch-in, violating the contract. | POST `{"emp_code":"EMP0001", "status":"ABSENT"}` → 201 with an ABSENT record that has a punch_in. | Replaced with Pydantic `@field_validator` accepting only `PRESENT`, `WFH`, `ON_DUTY`. |
| 21 | `POST /attendance/punch-in` – response includes `id` field (L119) | `doc["id"] = str(res.inserted_id)` adds an `id` key that must not appear in responses. The contract says records have no id in the API. | Response body contains `"id": "6879..."` — extra field fails schema validation. | Removed the line; `doc.pop("_id", None)` alone is sufficient; apply `_ser_attendance()` for clean serialisation. |
| 22 | `POST /attendance/punch-in` – `punch_in` not serialised to epoch ms (L119–121) | `doc["punch_in"]` is a `datetime` object; FastAPI JSON-serialises it as an ISO string, not an integer. | Response field `punch_in` is `"2026-07-06T04:35:00"` instead of `1751775900000`. | Applied `_ser_attendance()` before returning. |
| 23 | `GET /attendance` – loads all matching docs into memory (L144) | `list(db.attendance_logs.find(q))` fetches every matching document before Python-side sorting and slicing. On 100k records this is a full collection scan with huge memory consumption. | Latency / OOM under load; grader's performance test will time out. | Pushed sort, skip, and limit into the MongoDB query; use `count_documents(q)` for total. |
| 24 | `GET /attendance` – Python-only sort misses secondary key (L145) | `docs.sort(key=lambda d: d["date"], reverse=True)` sorts only by date; missing secondary sort by `emp_code` ascending. | Records on the same date appear in non-deterministic order. | Replaced with `.sort([("date", -1), ("emp_code", 1)])` on the cursor. |
| 25 | `GET /attendance` – response exposes `id` (L149) | `d["id"] = str(d.pop("_id"))` adds a synthetic `id` key to every returned document. | Response body contains `"id": "..."` which is not part of the `AttendanceRecord` schema. | Used `{"_id": 0}` projection in `find()`; apply `_ser_attendance()`. |
| 26 | `GET /attendance` – no date_from > date_to → 422 check | The starter silently accepts and queries with an impossible date range, returning an empty set instead of 422. | `GET /attendance?date_from=2026-08-01&date_to=2026-07-01` → 200 with empty items instead of 422. | Added explicit guard: `if date_from and date_to and date_from > date_to: raise HTTPException(422, ...)`. |
| 27 | `GET /attendance` – no page_size max validation | `page_size` is an unconstrained `int`; passing `page_size=10000` fetches huge result sets. | `GET /attendance?page_size=99999` works without error. | Added `Query(..., ge=1, le=100)` constraint (R10). |
| 28 | `POST /attendance/punch-out` – pre-filtering `punch_in <= punched_at` masked 422 as 404 | When client sends `punched_at <= punch_in`, filtering by `punch_in <= punch_out` in `find_one` caused query to match nothing and return 404 instead of required 422 validation error. | Punch-out with timestamp earlier than punch-in returned 404 instead of 422. | Query latest record with `punch_in != None`, then validate `punched_at <= punch_in` explicitly with 422. |
| 29 | `late_leaderboard` – `$setWindowFields` compound sortBy rejected by MongoDB `$rank` | Passing compound `sortBy: {"total_late_minutes": -1, "_id": 1}` causes MongoDB error 5371602: `$rank must be specified with a top level sortBy expression with exactly one element`. | Running `/analytics/leaderboard/late` against MongoDB raised 500 OperationFailure. | Changed `$setWindowFields` sortBy to single key `{"total_late_minutes": -1}`; secondary tie-breaker sort placed in following `$sort` stage. |

**Items examined and decided NOT defects:**
- The `IST` timezone object on L25 is defined correctly (`timedelta(hours=5, minutes=30)`).
- The `model_dump()` call in `create_employee` is correct Pydantic v2 usage (not `dict()`).
- `db.attendance_logs.insert_one(doc)` modifies `doc` in-place to add `_id`; the subsequent `pop("_id")` correctly removes it.
